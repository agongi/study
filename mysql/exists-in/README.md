# Exists vs In
```
> mysql 8.4 에서 exists vs in 쿼리의 성능 및 동작원리 비교
```

✦ MySQL 8.4 버전에서 EXISTS와 IN의 성능 및 동작 원리를 비교 설명해 드리겠습니다.

과거에는 "서브쿼리의 결과가 작으면 IN, 크면 EXISTS가 유리하다"는 것이 일반적인 통념이었지만, MySQL 8.0 이상 버전부터는 옵티마이저(Optimizer)가 매우 발전하여 대부분의 경우 두 구문을 서로
변환하여 최적의 실행 계획을 수립합니다.

따라서 현대의 MySQL에서는 성능 차이가 거의 없는 경우가 많지만, 동작 원리의 근본적인 차이를 이해하고 특정 상황에 더 적합한 구문을 선택하는 것은 여전히 중요합니다.

1. 핵심 동작 원리 비교

가장 큰 차이는 쿼리의 주도권(Driving Table)을 누가 갖는가에 있습니다.

* `IN`: 서브쿼리(안쪽 쿼리)를 먼저 실행하여 결과 집합(Set)을 메모리나 임시 테이블에 만든 후, 메인 쿼리(바깥쪽 쿼리)의 각 행과 결과 집합을 비교하며 조건에 맞는지 확인합니다.
  * 동작 순서: 안쪽 쿼리 실행 → 결과 저장 → 바깥쪽 쿼리 실행 및 비교
  * 비유: "참석자 명단(IN 서브쿼리)을 미리 다 받아놓고, 들어오는 사람(메인 쿼리)이 명단에 있는지 일일이 대조하는 방식"

* `EXISTS`: 메인 쿼리(바깥쪽 쿼리)를 먼저 실행하면서 각 행의 값을 서브쿼리로 넘겨 조건을 만족하는 행이 하나라도 존재하는지(Exist) 확인합니다. 조건을 만족하는 행을 하나라도 찾으면 즉시
  서브쿼리 실행을 멈추고 TRUE를 반환합니다. (Short-circuit)
  * 동작 순서: 바깥쪽 쿼리 실행 → (한 행마다) 안쪽 쿼리 실행 및 조건 확인
  * 비유: "들어오는 사람(메인 쿼리)마다, 그 사람이 속한 팀이 있는지 다른 방(서브 쿼리)에 가서 확인해보는 방식. 팀원이 한 명이라도 있으면 바로 확인을 멈추고 '있음'이라고 보고함."

2. 성능 비교: 전통적 관점 vs MySQL 8.4의 현실

전통적인 성능 규칙
* `IN`이 유리한 경우: 서브쿼리(안쪽)의 결과 집합이 메인 쿼리(바깥쪽)보다 현저히 작을 때.
  * 예: 전체 사용자(메인 쿼리, 1억 명) 중 VIP 회원(서브쿼리, 100명) 목록에 포함된 사용자를 찾을 때.
* `EXISTS`가 유리한 경우: 메인 쿼리(바깥쪽)의 결과 집합이 서브쿼리(안쪽)보다 현저히 작을 때.
  * 예: 특정 부서의 직원(메인 쿼리, 50명)들이 전체 주문 내역(서브쿼리, 1억 건)에 존재하는지 확인할 때.


MySQL 8.4의 현실: 옵티마이저의 역할
MySQL 8.4의 옵티마이저는 매우 영리해서 IN 구문을 보고도 내부적으로 EXISTS나 SEMI-JOIN과 같은 더 효율적인 형태로 변환하여 실행하는 경우가 많습니다.


* `IN` → `SEMI-JOIN` 변환: 옵티마이저는 IN 서브쿼리를 JOIN과 유사한 SEMI-JOIN으로 변환하여 처리합니다. SEMI-JOIN은 JOIN처럼 테이블을 연결하지만, 중복된 값을 제거하고 일치하는 첫 번째
  행만 찾으면 탐색을 중단하는 등 EXISTS와 유사한 최적화가 적용됩니다.

결론적으로, 대부분의 상황에서 개발자가 `IN`과 `EXISTS` 중 무엇을 선택하든 MySQL 옵티마이저가 최적의 실행 계획으로 변환해주므로 성능 차이가 거의 없습니다.

3. 언제 무엇을 써야 할까? (권장 사항)

3-1. 가독성을 우선하라: 팀원들이나 본인이 이해하기 더 쉬운 형태로 쿼리를 작성하세요. 대부분의 경우 IN이 더 직관적입니다.


3-2. `NOT IN` vs `NOT EXISTS`:
  * NOT IN은 서브쿼리 결과에 NULL이 하나라도 포함되면 전체 결과가 빈 집합(empty set)이 되는 심각한 문제가 있습니다.
  * 반면 NOT EXISTS는 NULL 값에 영향을 받지 않아 훨씬 안전하고 예측 가능합니다.
  * 따라서 부정형 비교를 할 때는 `NOT IN` 대신 `NOT EXISTS`를 사용하는 것이 강력히 권장됩니다.


3-3. `EXPLAIN`으로 확인하라: 성능에 민감한 중요한 쿼리라면, IN과 EXISTS 두 가지 버전으로 작성해보고 EXPLAIN 명령어를 통해 실제 실행 계획을 비교해보는 것이 가장 확실한 방법입니다. 실행
   계획이 동일하다면 어떤 것을 사용해도 무방합니다.

예제

    1 -- employees 테이블에서 department_id가 departments 테이블에 존재하는 직원 찾기
    2
    3 -- IN 사용 (가독성이 좋음)
    4 SELECT name
    5 FROM employees
    6 WHERE department_id IN (SELECT id FROM departments);
    7
    8 -- EXISTS 사용 (상관 서브쿼리)
    9 SELECT e.name
10 FROM employees e
11 WHERE EXISTS (SELECT 1 FROM departments d WHERE d.id = e.department_id);
12
13 -- JOIN 사용 (옵티마이저가 IN/EXISTS를 변환하는 최종 형태와 유사)
14 SELECT DISTINCT e.name
15 FROM employees e
16 INNER JOIN departments d ON e.department_id = d.id;


MySQL 8.4에서 위 세 쿼리의 EXPLAIN을 실행해보면, 옵티마이저에 의해 매우 유사하거나 동일한 실행 계획으로 처리될 가능성이 높습니다.

최종 요약

* 동작 원리: IN은 서브쿼리를 먼저 실행하여 결과 목록을 만들고 비교, EXISTS는 메인 쿼리의 행을 하나씩 서브쿼리에서 확인.
* 성능: MySQL 8.4에서는 옵티마이저가 IN을 EXISTS나 SEMI-JOIN으로 자동 변환하므로 성능 차이가 거의 없는 경우가 대부분이다.
* 권장 사항:
  * 일반적으로는 가독성이 좋은 `IN`을 사용한다.
  * 부정형 쿼리에서는 NULL 문제 때문에 `NOT EXISTS`를 사용한다.
  * 성능이 의심될 때는 `EXPLAIN`으로 실제 실행 계획을 확인하는 것이 정답이다.
