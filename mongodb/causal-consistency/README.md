MongoDB의 인과적 일관성(Causal Consistency), 읽기 관심(Read Concern), 쓰기 관심(Write Concern)에 대해 쉽게 설명해 드릴게요.

데이터베이스, 특히 여러 서버에 데이터를 복제하여 사용하는 분산 데이터베이스(MongoDB도 해당)에서 중요한 개념입니다.

비유로 이해하기: "단체 채팅방"

여러분이 여러 명과 함께 있는 단체 채팅방을 상상해 보세요.

1. 나: "오늘 저녁 메뉴는 피자 어때요?" (쓰기 작업 1)
2. 친구 A: "좋아요!" (쓰기 작업 2)
3. 나: "그럼 피자 주문할게요." (쓰기 작업 3)

이 대화는 순서대로 이뤄져야 의미가 통합니다. 만약 여러분이 이 메시지들을 순서가 뒤죽박죽으로 보게 된다면 대화의 흐름을 이해할 수 없겠죠?

- 잘못된 순서: "그럼 피자 주문할게요." -> "오늘 저녁 메뉴는 피자 어때요?" -> "좋아요!" (???)

인과적 일관성은 바로 이처럼, 원인과 결과 관계에 있는 작업들이 논리적인 순서대로 실행되고 조회되는 것을 보장하는 모델입니다.

내가 피자를 제안했기 때문에(원인) 친구 A가 동의했고(결과), 그래서 내가 주문을 한 것입니다. 이 순서가 지켜지는 것이 바로 인과적 일관성입니다.

## 1. 쓰기 관심 (Write Concern): "내 메시지가 몇 명에게 전달되어야 안심할까?"
writeConcern은 내가 보낸 메시지(데이터 쓰기)가 그룹 채팅방의 몇몇 멤버에게 확실히 전달되었는지 확인하는 과정입니다.

* w: 1 (기본값): 메시지를 보내고, 채팅방의 대표(Primary) 서버 한 곳에만 메시지가 기록되면 "전송 완료!"라고 생각합니다. 빠르지만, 만약 그 대표 서버가 바로
  고장 나면 메시지가 사라질 수 있습니다.
* w: "majority": 채팅방 멤버의 과반수에게 내 메시지가 전달된 것을 확인할 때까지 기다립니다. 예를 들어 5명 중 3명에게 전달되면 "전송 완료!"라고 봅니다. 약간
  느릴 수 있지만, 대표 서버가 고장 나도 다른 멤버들이 메시지를 가지고 있으므로 훨씬 안전합니다.

## 2. 읽기 관심 (Read Concern): "어떤 버전의 대화 내용을 볼까?"
readConcern은 내가 채팅방의 대화 내용을 읽을 때(데이터 읽기) 어떤 상태의 메시지까지 볼 것인지 결정하는 것입니다.

* level: "local": 그냥 지금 내 휴대폰에 보이는 대로 대화 내용을 읽습니다. 아직 다른 사람들에게 전달되지 않은, 대표 서버에만 막 도착한 메시지도 보일 수
  있습니다. 가장 빠르지만, 아직 확정되지 않은 내용을 볼 수도 있습니다.
* level: "majority": 채팅방 멤버의 과반수가 "이 메시지는 확실히 받았어"라고 인정한 내용만 읽습니다. 즉, 여러 서버에 복제되어 안정성이 보장된 데이터만 보는
  것입니다. writeConcern: "majority"와 함께 사용할 때 가장 강력한 일관성을 제공합니다.

## 3. 인과적 일관성을 위한 조합
MongoDB에서 가장 강력한 인과적 일관성을 보장받으려면, 클라이언트 세션에서 다음과 같이 설정합니다.

* `Write Concern: majority` (과반수가 쓸 내용을 확인해야 쓰기 성공)
* `Read Concern: majority` (과반수가 확인한 내용만 읽기)

이렇게 하면 내가 쓴 내용은 반드시 과반수에게 복제된 후에야 성공으로 처리되고, 내가 읽는 내용은 항상 과반수에 의해 확인된 안정적인 데이터이므로, 작업의 인과
관계가 절대 깨지지 않습니다.

## 4. 요약
* 인과적 일관성: "피자 제안 -> 동의 -> 주문"처럼, 원인과 결과 순서가 지켜지는 것.
* Write Concern: 내 쓰기 작업이 얼마나 많은 서버에 복제되어야 성공으로 칠지 결정. (majority가 안전)
* Read Concern: 얼마나 안정적으로 복제된 데이터를 읽을지 결정. (majority가 안정)

이 두 가지를 majority로 설정하면, 분산된 MongoDB 환경에서도 데이터의 논리적 순서를 확실하게 보장받을 수 있습니다.
